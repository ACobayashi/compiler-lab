\subsection{成员B：C17/Clang/LLVM 编译流程实验}
成员B使用一份独立的 C17 程序完成本小题。程序里有宏、数组、循环、条件分支和全局变量，适合从源码一路看到预处理、前端分析、IR、汇编、目标文件和链接结果。实验在 Ubuntu 22.04 Docker 容器中完成，使用 Clang/LLVM 14.0.0、GCC 11.4.0 和 Graphviz 2.43.0；中间表示观察 x86-64 LLVM IR，目标代码部分观察 AArch64 汇编和目标文件。

\subsubsection{源程序与预处理}
程序读入 $1$ 至 $8$ 个整数。宏 \texttt{ADJUST(value,bias)} 将数组元素乘以比例常数后加上偏置；\texttt{weighted\_sum} 根据计算值的奇偶性累加或扣减，并更新全局计数器 \texttt{processed\_items}。源文件和头文件保存在仓库的 \texttt{pipeline/memberB/q1/} 目录中，原始输入为 \texttt{5} 与 \texttt{1 2 3 4 5}。

\lstinputlisting[language=C,caption={实验使用的 C17 源程序},label={lst:memberb-c-source}]{../pipeline/memberB/q1/src/main.c}
\lstinputlisting[language=C,caption={宏与数组长度定义},label={lst:memberb-config}]{../pipeline/memberB/q1/include/config.h}

使用预处理选项只执行头文件展开和宏替换，输出写入 \texttt{main.i}：
\begin{lstlisting}[language=bash]
mkdir -p build/memberB/q1
clang -E -std=c17 -Ipipeline/memberB/q1/include \
  pipeline/memberB/q1/src/main.c -o build/memberB/q1/main.i
\end{lstlisting}
预处理结果中，\texttt{stdio.h} 的声明被展开，\texttt{MAX\_ITEMS} 在数组声明中替换为 \texttt{8}，\texttt{ADJUST(values[i], global\_bias)} 展开为 \texttt{((values[i]) * 3 + (global\_bias))}。因此 \texttt{.i} 文件保留了原有计算逻辑，但已不再依赖这两个宏定义。

\subsubsection{词法、语法与语义分析证据}
词法阶段用 Clang 的 token dump 输出 token 种类、词素和源码位置；语法树转储则展示函数、声明、循环、条件分支及表达式的嵌套关系。两个命令都以 \texttt{-fsyntax-only} 避免生成目标文件：
\begin{lstlisting}[language=bash]
mkdir -p build/memberB/q1
clang -std=c17 -Ipipeline/memberB/q1/include -fsyntax-only \
  -Xclang -dump-tokens pipeline/memberB/q1/src/main.c \
  2> build/memberB/q1/tokens.txt
clang -std=c17 -Ipipeline/memberB/q1/include -fsyntax-only \
  -Xclang -ast-dump pipeline/memberB/q1/src/main.c \
  > build/memberB/q1/ast.txt
\end{lstlisting}
图~\ref{fig:q1b-tokens} 中可看到 \texttt{weighted\_sum}、\texttt{for}、比较与算术运算符等 token 以及它们在 \texttt{src/main.c} 中的行列位置。图~\ref{fig:q1b-ast} 展示了 AST 中的 \texttt{FunctionDecl}、\texttt{ForStmt}、\texttt{IfStmt}、\texttt{BinaryOperator} 等节点；节点的类型注记也表明 Clang 已完成语法解析和类型语义检查。此处观察的是编译器对合法程序的成功分析，不是单独构造错误程序验证诊断。

\labfigure{figures/memberB/q1/ast.png}{Clang AST 中的函数、循环与条件节点}{fig:q1b-ast}

\subsubsection{控制流图与 LLVM IR}
为直接观察控制流图，GCC 在编译时写出 tree/CFG 图文件，再由 Graphviz 将 \texttt{.dot} 文件绘制为图~\ref{fig:q1b-cfg}。其中循环回边对应 \texttt{for} 的重复执行，条件分支对应奇偶判断以及 \texttt{main} 中的输入合法性检查。
\begin{lstlisting}[language=bash]
mkdir -p build/memberB/q1/gcc-graphs
gcc -O0 -Ipipeline/memberB/q1/include -fdump-tree-all-graph \
  -dumpdir build/memberB/q1/gcc-graphs/ -dumpbase main-gcc \
  -c pipeline/memberB/q1/src/main.c -o build/memberB/q1/main-gcc.o
dot -Tpng build/memberB/q1/gcc-graphs/main-gcc.015t.cfg.dot \
  -o build/memberB/q1/gcc-graphs/main-cfg.png
\end{lstlisting}
\labfigure{figures/memberB/q1/cfg.png}{GCC 生成并由 Graphviz 绘制的控制流图}{fig:q1b-cfg}

LLVM IR 由 Clang 前端从同一份 C 源码生成。\texttt{-O0} 保留较多局部存储、\texttt{load/store} 与显式控制流，便于将 IR 与源码逐句对应；图~\ref{fig:q1b-ir-o0} 展示了函数定义、数组操作、比较和分支。
\begin{lstlisting}[language=bash]
clang -std=c17 -Ipipeline/memberB/q1/include -O0 -S -emit-llvm \
  pipeline/memberB/q1/src/main.c -o build/memberB/q1/main-O0.ll
\end{lstlisting}
\labfigure{figures/memberB/q1/ir-o0.png}{未优化 LLVM IR：函数、基本块与内存操作}{fig:q1b-ir-o0}

\subsubsection{优化前后比较与目标代码生成}
以相同源程序分别使用 \texttt{-O0} 和 \texttt{-O2} 生成 IR，构成参数对照。图~\ref{fig:q1b-ir-opt} 中，优化版本的局部计算更倾向于使用 SSA 临时值，减少部分冗余栈读写，并带有 \texttt{nsw} 等运算属性；函数属性、循环组织也有变化。优化并不改变本程序的可观察输入输出，但 IR 不再是源代码逐行翻译的形式。
\begin{lstlisting}[language=bash]
clang -std=c17 -Ipipeline/memberB/q1/include -O2 -S -emit-llvm \
  pipeline/memberB/q1/src/main.c -o build/memberB/q1/main-O2.ll
\end{lstlisting}
\labfigure{figures/memberB/q1/ir-o0-o2.png}{同一函数在 -O0 与 -O2 下的 LLVM IR 对照}{fig:q1b-ir-opt}

目标代码阶段使用 LLVM 后端将 IR 映射为 AArch64 汇编。该汇编出现了 32 位/64 位通用寄存器、条件分支和数组寻址指令；汇编器再把文本指令编码为 AArch64 机器码。目标文件为可重定位 ELF，仍包含需要链接器处理的符号与重定位项。
\begin{lstlisting}[language=bash]
clang --target=aarch64-linux-gnu -std=c17 \
  -Ipipeline/memberB/q1/include -O2 -S -emit-llvm \
  pipeline/memberB/q1/src/main.c -o build/memberB/q1/main-O2-aarch64.ll
llc -O2 build/memberB/q1/main-O2-aarch64.ll \
  -o build/memberB/q1/main-O2-aarch64.s
aarch64-linux-gnu-gcc -c build/memberB/q1/main-O2-aarch64.s \
  -o build/memberB/q1/main-O2-aarch64.o
aarch64-linux-gnu-readelf -h build/memberB/q1/main-O2-aarch64.o
aarch64-linux-gnu-readelf -Ws -rW build/memberB/q1/main-O2-aarch64.o
\end{lstlisting}
图~\ref{fig:q1b-asm} 是 AArch64 汇编片段；图~\ref{fig:q1b-object} 的 ELF 头中 \texttt{Type: REL} 与 \texttt{Machine: AArch64} 说明产物是尚未链接的可重定位目标文件。图~\ref{fig:q1b-symrel} 中，自定义函数和全局变量进入符号表，\texttt{printf}/\texttt{scanf} 等外部函数仍是未定义符号；\texttt{R\_AARCH64\_*} 重定位项记录了链接时需要修补的位置。
\labfigure{figures/memberB/q1/asm-aarch64.png}{LLVM 后端生成的 AArch64 汇编}{fig:q1b-asm}
\labfigure{figures/memberB/q1/object-elf.png}{AArch64 可重定位目标文件的 ELF 头}{fig:q1b-object}
\labfigure{figures/memberB/q1/symbols-relocs.png}{目标文件的符号表与重定位表}{fig:q1b-symrel}

\subsubsection{链接、反汇编与运行验证}
将目标文件与 C 运行时库链接后，外部函数调用可解析为可执行文件中的动态链接入口。图~\ref{fig:q1b-link} 对照了链接前后的反汇编：目标文件中保留针对 \texttt{printf} 的调用重定位，链接后的程序则显示具体地址和 \texttt{printf@plt} 调用入口。AArch64 可执行文件不能直接作为 macOS arm64 原生程序运行；本实验在 Ubuntu 容器中通过 QEMU 用户态执行，并用同一组输入检查结果。
\begin{lstlisting}[language=bash]
clang -std=c17 -Ipipeline/memberB/q1/include -O2 \
  pipeline/memberB/q1/src/main.c -o build/memberB/q1/main-native
build/memberB/q1/main-native < pipeline/memberB/q1/input/sample.txt
aarch64-linux-gnu-gcc -no-pie build/memberB/q1/main-O2-aarch64.o \
  -o build/memberB/q1/main-aarch64
qemu-aarch64 -L /usr/aarch64-linux-gnu \
  build/memberB/q1/main-aarch64 < pipeline/memberB/q1/input/sample.txt
\end{lstlisting}
样例数据为 $1,2,3,4,5$，调整值分别为 $5,8,11,14,17$，按奇偶规则计算得到 $-11$，处理数为 $5$。报告截图中的目标文件/链接证据来自 AArch64 目标；以上原生编译命令用于验证同一 C 源程序的运行语义。
\labfigure{figures/memberB/q1/link-disassembly.png}{链接前目标文件与链接后程序的反汇编对照}{fig:q1b-link}

\subsubsection{阶段观察小结}
本小题中，\texttt{MAX\_ITEMS} 在预处理文件中替换为 \texttt{8}，\texttt{ADJUST(value,bias)} 展开为“元素乘以 \texttt{SCALE\_FACTOR} 后加 \texttt{global\_bias}”的表达式。\texttt{weighted\_sum} 的 token、AST、CFG 和 LLVM IR 分别保留了循环、奇偶分支和对 \texttt{processed\_items} 的更新；\texttt{-O2} 相比 \texttt{-O0} 减少了重复的内存读写。AArch64 目标文件中的符号和重定位项、以及链接后的反汇编说明了 \texttt{printf} 等外部调用在链接阶段得到处理。样例输入 \texttt{1 2 3 4 5} 的结果为 \texttt{result=-11, processed=5}，与源码中的计算一致。
